### C1. Unilateral settlement: opponent can settle a waived match with NO proposed result and take rating + wager
- file: `supabase/leagues.sql:402`
- lens: settlement  |  class: C5 money / C4 missing done-guard

**What it is:** report_match_result's single-report branch (supabase/match-disputes.sql:63-66) sets the match to 'pending_confirmation' WITHOUT stamping winner_id, result, or result_proposed_by (all stay NULL). confirm_match_result (live body: supabase/leagues.sql:388-414) only blocks self-confirmation via `if auth.uid() = m.result_proposed_by` - with result_proposed_by NULL that comparison is NULL (not true), so EITHER competitor passes and it calls _settle_match(m.id, NULL, NULL, ...). In the authoritative _settle_match (supabase/ror-symmetric-stake.sql:65-97), p_result NULL falls through the draw check into the DECISIVE branch, and `elsif p_winner_id = m.challenger_id` is NULL-false, so the ELSE arm awards the full transfer (stake + m.wager) to the OPPONENT and debits the challenger, then writes status='completed' with winner_id NULL and result NULL. W/L counters don't move (NULL guards) but rating and the wager DO. Exploit: accept anyone's waived challenge (or lure a victim into accepting yours where you are opponent), attach any video (competitors can), call report_match_result once (moves status to pending_confirmation), then confirm_match_result(true). The challenger loses stake+wager with zero agreement, and gets a 'You lost to X' notification for a fight that never happened. Same hole re-opens after a decline: confirm(false) nulls winner/result back to pending_referee, one report re-enters pending_confirmation with NULL proposer.

**Repro:** As opponent of any waived (referee_waived) match with >=1 video: rpc report_match_result(match_id, <anything>, 'submission') then rpc confirm_match_result(match_id, true). Match completes with result NULL, your rating += stake+wager, victim's rating -= same.

**Fix:** In confirm_match_result raise if m.result_proposed_by IS NULL or m.result IS NULL (nothing was proposed - dual-report matches must settle only through report_match_result agreement). Defense-in-depth in _settle_match: raise if p_result IS NULL, and if p_result <> 'draw' require p_winner_id in (m.challenger_id, m.opponent_id). Apply in a new run-last SQL file (do not edit ror-symmetric-stake body ownership without re-running it).

**Verify on prod:**
```sql
select id, challenger_id, opponent_id, wager, completed_at from public.matches where status='completed' and (result is null or (result <> 'draw' and (winner_id is null or winner_id not in (challenger_id, opponent_id)))) order by completed_at desc limit 50;
```

### C2. Anyone can create, join and DELETE tournament teams in any event (tournament_teams / tournament_team_members RLS + ungated add_team_member)
- file: `supabase/tournaments-pro.sql:134`
- lens: tournaments  |  class: C2 RLS gaps + C1 default EXECUTE grants

**What it is:** Three separate holes stack on the tournament team tables, and the league equivalents (league-teams.sql) have none of them:

1. `ttiteams_write` (tournaments-pro.sql:134-136) is `for all to authenticated using/with check (is_tournament_host(tournament_id) OR captain_id = auth.uid())`. A direct PostgREST INSERT with `captain_id = <me>` passes the WITH CHECK for ANY tournament_id, regardless of the event's `team_build` setting or status. That bypasses `create_tournament_team` (line 290), which at least gates on host-or-captain-build. The same policy's USING clause then lets that user UPDATE (incl. `seed`, which drives bracket seeding) and DELETE the row. `tournament_bouts.a_team/b_team` are ON DELETE SET NULL (lines 77-78), so deleting the team mid-event silently blanks live bracket slots.
2. `ttmembers_write` (line 141-151) permits any authenticated user to INSERT/DELETE their own `tournament_team_members` row on ANY team, bypassing the `team_size` cap in `add_team_member` and letting an outsider self-insert into a rival team's roster.
3. `add_team_member` (line 299-309) is SECURITY DEFINER with NO caller check at all - not host, not captain, not self. It keeps Postgres' default PUBLIC EXECUTE (it is not underscore-prefixed, so neither harden-internal-functions.sql:36-48 nor tournament-auto-mats.sql:154-159 revokes it). Any caller can put any user on any team.

`record_subbout` rebuilds the roster array from `tournament_team_members` on every call (lines 634-635), so a roster mutated between sub-bouts changes who is recorded as fighting.

**Repro:** As any signed-in user: POST /rest/v1/tournament_teams {"tournament_id":"<someone else's event>","name":"ghost","captain_id":"<my uid>"} -> 201. Host taps Generate; the ghost team is seeded by _tournament_seeds (line 385). Then DELETE /rest/v1/tournament_teams?id=eq.<ghost> -> every bout referencing it now has a null team slot and the bracket cannot be completed. Separately: POST /rest/v1/rpc/add_team_member {"p_team":"<any team>","p_user":"<any profile id>"} succeeds with no authorization.

**Fix:** Replace both write policies with host-only (or drop them entirely and route all writes through RPCs, exactly as league_teams / league_team_members do - they have read-only policies at league-teams.sql:55-58). Add `if not (is_tournament_host(tid) or captain of p_team) then raise exception` to `add_team_member`, plus the roster-freeze check that `add_league_team_member` already has (league-teams.sql:108-115), and revoke/re-grant EXECUTE deliberately.

**Verify on prod:**
```sql

```

### C3. video-url: unvalidated path lets any signed-in user read, overwrite, or delete ANY object in the R2 match-videos bucket (prefix check is defeated by ../)
- file: `supabase/functions/video-url/index.ts:72`
- lens: edge-fns  |  class: C2 (authorization bypass via unconstrained key) / C11

**What it is:** All three ops derive authorization from the first path segment and then presign the raw string.
- upload (line 60-73): `stamp` is taken straight from the body with no validation (`String(body?.stamp ?? '')`), then `path = `${matchId}/${stamp}.${ext}``. The caller only has to be a participant of `matchId` - trivially satisfied by challenging anyone, since they are then the challenger of their own match.
- play (line 76-91) and delete (line 93-107): `matchId = path.split('/')[0]` is what the participation / is_public check runs against, but the FULL attacker-supplied `path` is what gets presigned or DELETEd.

presign() (line 36-40) builds `new Request(url)`, and the WHATWG URL parser removes dot segments BEFORE aws4fetch signs, so the signature is computed over the escaped key. I verified this locally with the repo's own aws4fetch: signing `https://acct.r2.cloudflarestorage.com/match-videos/AAAA/../BBBB/secret.mp4` yields a valid presigned URL for `/match-videos/BBBB/secret.mp4`. The same normalization applies to the `r2.fetch(... {method:'DELETE'})` on line 105.

Impact: with any known key, any authenticated user gets (a) a 1-hour public GET URL for a private match video, including a minor's, (b) a PUT that overwrites it with arbitrary content, (c) an outright DELETE. Keys of every PUBLIC match's video are directly readable by everyone through the match_videos SELECT policy (supabase/videos.sql:71-80), so parts (b) and (c) are exploitable today with zero guesswork against every public video in the app; private keys are `<match_id>/<epoch_ms>.<ext>` and brute-forceable for a targeted victim.

**Repro:** 1. Sign in as any user, create a challenge so you are a participant of match M.
2. POST to /functions/v1/video-url with {op:'upload', matchId:M, stamp:'../<victim_match_id>/<victim_stamp>', ext:'mp4'} -> returns a presigned PUT for the victim's key; PUT anything to it and the victim's video is replaced.
3. Same with {op:'play', path:'<M>/../<victim_match_id>/<victim_stamp>.mp4'} -> presigned GET for a private video you may not view.
4. Same with {op:'delete', path:'<M>/../<victim_match_id>/<victim_stamp>.mp4'} -> the victim's file is deleted from R2 while their match_videos row survives (permanently broken playback).

**Fix:** Never let the client contribute path structure. For upload, generate the key server-side: `const path = `${matchId}/${crypto.randomUUID()}.${ext}`` (ignore `stamp` entirely, or validate it with /^[0-9]{1,20}$/). For play/delete, reject any path that does not match /^[0-9a-f-]{36}\/[A-Za-z0-9._-]+$/ and additionally require `path.startsWith(matchId + '/')` after the regex; also reject any path containing '..', '%2e', backslashes, or a leading '/'.

**Verify on prod:**
```sql
-- how many stored rows already violate the intended <match_id>/<file> invariant
select count(*) as bad_paths from public.match_videos where path not like match_id::text || '/%' or path like '%..%';
```

### H1. league_members UPDATE lets any user move their own membership row into ANY league - private-league infiltration + join_code disclosure
- file: `supabase/leagues-hardening.sql:70`
- lens: rls-grants  |  class: C2

**What it is:** The hardened policy is:

  create policy "league_members_update" on public.league_members for update to authenticated
    using ( user_id = auth.uid() or <creator of OLD.league_id> )
    with check ( (user_id = auth.uid() and role = 'member') or <creator of NEW.league_id> );

The WITH CHECK constrains user_id and role but says NOTHING about league_id, and - unlike the sibling fix three lines further down for league_fixtures (leagues-hardening.sql:88-89 `revoke update ... grant update (match_id)`) and unlike the profiles pattern used everywhere else (schema.sql:267, social.sql:68) - there is no `revoke update on public.league_members from authenticated`. Supabase's default `grant all on all tables in schema public to authenticated` therefore leaves a full-row UPDATE available.

Because league_members' PK is (league_id, user_id), an UPDATE that changes league_id MOVES the membership row. USING is evaluated on the OLD row (user_id = auth.uid() passes) and WITH CHECK on the NEW row (user_id = auth.uid(), role = 'member' passes). Nothing checks that the destination league is `visibility = 'open'` or that the caller holds an invite - which is exactly the control the INSERT policy at line 63-68 was written to enforce. The UPDATE path walks straight around it.

The league id needed is trivially discoverable: league_members_read is still `using (true)` (supabase/leagues.sql:95), so `select distinct league_id from league_members` returns every league id in the system, private ones included.

Once the row lands in the private league the attacker is an active member, so: (a) leagues_read (leagues-hardening.sql:43-50) now returns the league row INCLUDING `join_code` (leagues.sql:32), which they can reshare; (b) `lm_read_members` on league_messages (push-notifications.sql:143-148) gates purely on a league_members row, so all private league announcements become readable; (c) they are included in generate_league_week pairing and league_standings; (d) the same UPDATE can set `joined_week = 1` (retro-pairing) and flip `active` back to true after an organizer deactivated them, so an organizer cannot remove them (league_members_leave only lets the creator DELETE, and the attacker can re-INSERT/re-UPDATE).

The file header at leagues-hardening.sql:14-16 explicitly lists "join private leagues, retro-pair" as the finding being closed. The INSERT half was closed; the UPDATE half was not.

**Repro:** As any authenticated user: 1) join any open league (or create one) so you own a league_members row. 2) `select distinct league_id from league_members` to enumerate every league id, including private/kids leagues. 3) PostgREST: `supabase.from('league_members').update({ league_id: '<private-league-uuid>', role: 'member', joined_week: 1, active: true }).eq('league_id','<my-open-league>').eq('user_id', myId)`. 4) `select * from leagues where id = '<private-league-uuid>'` now returns the row with join_code; `select * from league_messages where league_id = ...` returns the private announcements.

**Fix:** Mirror the league_fixtures treatment: `revoke update on public.league_members from authenticated;` and grant only the columns a member legitimately edits (realistically none - `active` self-deactivation can go through a SECURITY DEFINER RPC). At minimum add `league_id` immutability to the WITH CHECK, e.g. require the NEW league_id to be an open league or one the caller holds a pending invite for, and re-assert `role = 'member'`. Also tighten league_members_read (see the separate using(true) finding) so private league ids are not enumerable.

**Verify on prod:**
```sql
select polname,
       pg_get_expr(polqual, polrelid)      as using_expr,
       pg_get_expr(polwithcheck, polrelid) as check_expr
from pg_policy where polrelid = 'public.league_members'::regclass;

-- and: is UPDATE still table-wide (i.e. no column lock)?
select grantee, privilege_type, column_name
from information_schema.column_privileges
where table_schema='public' and table_name='league_members' and privilege_type='UPDATE';

-- has anyone already moved a row into a private league without an invite?
select lm.league_id, lm.user_id, lm.joined_week
from public.league_members lm
join public.leagues l on l.id = lm.league_id
where l.visibility = 'private'
  and l.created_by <> lm.user_id
  and not exists (select 1 from public.league_invites li
                  where li.league_id = lm.league_id and li.invited_user = lm.user_id);
```

### H2. leagues_read invite branch is dead: unqualified `id` binds to league_invites.id, so invited users cannot see the private league they were invited to
- file: `supabase/leagues-hardening.sql:48`
- lens: rls-grants  |  class: C2

**What it is:** The new leagues_read policy ends with:

    or exists (select 1 from public.league_invites li
               where li.league_id = id and li.invited_user = auth.uid() and li.status = 'pending')

`id` is unqualified. public.league_invites HAS its own `id uuid primary key` column (supabase/league-invites.sql:12), and PostgreSQL resolves an unqualified column reference against the INNERMOST query level first. So this compiles to `li.league_id = li.id`, which is never true for a real invite row - the branch can never grant visibility. (The league_members branch on line 47 is correct only by accident: league_members has no `id` column, so `m.league_id = id` does correlate to leagues.id.)

Result: a user invited to a PRIVATE league cannot read the leagues row at all until after they accept. Two concrete breakages in shipped code:
  * src/app/notifications.tsx:201 routes a `league_invite` notification to `/league/{lid}`. src/app/league/[id].tsx:57 calls fetchLeague(id), which returns null on the RLS miss (src/lib/leagues.ts:48-52 swallows the error), and lines 85-92 render the "League not found" empty state. Tapping the invite notification for a private league is a dead end.
  * The in-screen Accept invite / Decline invite buttons at src/app/league/[id].tsx:204-205 (fed by hasLeagueInvite at line 74) are unreachable for private leagues for the same reason - they only ever render for open leagues, where they are redundant.
The only surviving accept path is the invites card on the leagues index (src/app/leagues.tsx:106-117), which works because my_league_invites is SECURITY DEFINER.

**Repro:** Create a league with visibility='private'. From a second account that is NOT yet a member, invite it (invite_to_league). As the invitee: `select * from leagues where id = '<lid>'` returns 0 rows. In the app, tap the "League invite" notification -> lands on "League not found" with no way to accept from that screen.

**Fix:** Qualify the correlated reference: `where li.league_id = leagues.id and li.invited_user = auth.uid() and li.status = 'pending'`. Qualify the league_members branch the same way (`m.league_id = leagues.id`) so a future column addition cannot silently break it too. Re-run leagues-hardening.sql on prod.

**Verify on prod:**
```sql
-- Show the live policy body; look for the unqualified `id`:

from pg_policy
where polrelid = 'public.leagues'::regclass and polname = 'leagues_read';

-- Prove the branch is inert (expect 0):
select count(*) from public.league_invites li where li.league_id = li.id;

-- How many users are currently affected:
select count(*) from public.league_invites li
join public.leagues l on l.id = li.league_id

```

### H3. Founder family-tier entitlement can be silently clobbered by validate-purchase upsert (likely root cause of the 1-child cap)
- file: `supabase/functions/validate-purchase/index.ts:148`
- lens: sql-drift  |  class: C5/C3 - comp grants clobbered by paid path + data-migration drift

**What it is:** The junior-add cap is the RLS policy profiles_insert_managed_junior (supabase/family-plan.sql lines 160-171): unlimited children ONLY if has_active_family(auth.uid()); any other active entitlement allows exactly ONE child (count = 0 check). has_active_family (family-plan.sql:30-42) is true only when entitlements.product_id ilike '%family%'. **Fix:** Run the verify query; if any founder's product_id is not 'comp:founding-member-family', re-run admin-founders.sql (its backfill fixes 'comp:founding-member' rows) and add a guard in validate-purchase: never downgrade a source='comp' row whose product_id starts with 'comp:founding-member' (or store comp grants in a separate column/row so the store upsert cannot clobber them). ### H6. F-D root cause: founder's 1-child cap comes from plan != 'family', and the founder family tier hangs on a fragile product_id string that prod likely never has
- file: `src/app/juniors.tsx:32`
- lens: money-iap  |  class: C5
