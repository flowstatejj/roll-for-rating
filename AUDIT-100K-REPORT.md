## CRITICAL

### 1. grant_comp_entitlement() is callable by every authenticated user (default PUBLIC EXECUTE never revoked) — one RPC self-grants a free lifetime subscription, bypassing the paywall
- **File:** `supabase/subscriptions.sql:99`  | **Area:** rls-security / SECURITY DEFINER missing caller check / paywall bypass
- **What/why:** grant_comp_entitlement(p_user, p_note) is SECURITY DEFINER and contains NO caller check. The author's comment claims it is 'Not granted to authenticated; callable from the SQL editor or an edge function running as the service role.' That is false: in PostgreSQL a newly created function is granted EXECUTE to PUBLIC by default, and there is no `REVOKE EXECUTE ... FROM public` anywhere in the repo (grep of all supabase/*.sql found only 4 narrow revokes: kids_leaderboard x2, my_match_requests, submit_puzzle_written). The `authenticated` role is a member of PUBLIC, and PostgREST exposes every public-schema function as an RPC. So any logged-in user can POST /rest/v1/rpc/grant_comp_entitlement with their own uuid and receive source='comp' status='active' expires_at=null. has_active_entitlement() treats comp as never-expiring, so this is permanent free access. Same root cause exposes grant_comp_entitlement to grant comp to ANY user id, and the entitlements table's careful 'no client write policy' design is fully bypassed because the write happens inside a definer function running as the table owner.
- **At 100k users:** At 100k users this is a total revenue-model failure: word spreads that a single RPC call grants free lifetime access, so effectively zero users pay $4.99/$9.99. Also lets any user comp arbitrary accounts, polluting entitlements.
- **Evidence:** `create or replace function public.grant_comp_entitlement(p_user uuid, p_note text default null)
 returns void
 language sql security definer set search_path = public as $$
   insert into public.entitlements (user_id, product_id, source, status, expires_at)
   values (p_user, coalesce(p_note, 'comp'), 'comp', 'active', null)
   on conflict (user_id) do update
     set source = 'comp', status = 'active', expires_at = null, ...;
 $$;   -- NOTE: no `if not public.is_admin()` guard, and no `revoke execute ... from public`. Comment at line 96 wrongly assumes 'not granted' = not callable.`
- **Fix:** Add `revoke execute on function public.grant_comp_entitlement(uuid, text) from public, anon, authenticated;` immediately after the definition (and do the same defensively for every SECURITY DEFINER function that is meant to be internal/admin-only), OR add an internal `if not public.is_admin() then raise exception 'admins only'; end if;` guard. Prefer both. Audit every definer function in the repo for the same default-PUBLIC-execute exposure.

### 2. matches INSERT policy lets any client set status/winner/result_proposed_by directly - forged wins and forced rating theft from non-consenting users
- **File:** `supabase/schema.sql:278`  | **Area:** triggers-rpcs / missing constraint / authorization bypass
- **What/why:** RLS on public.matches allows INSERT with the ONLY check being challenger_id = auth.uid() (managed-juniors-phase2.sql:19-21 keeps the same shape). Unlike profiles (which has 'revoke insert on public.profiles from authenticated' + a column list in managed-juniors.sql:145-146), matches has NO column-level grant restriction anywhere in supabase/*.sql, and no BEFORE INSERT trigger checks status (trg_wager_band, trg_waive_safety, trg_minor_match, trg_not_banned, trg_not_blocked, trg_avatar_required all check other things). So a client with their JWT and the anon key can bypass the app and insert rows with arbitrary status, winner_id, result, submission_type, completed_at, tournament_id, result_proposed_by. Attack 1 (single account, forced rating theft): insert a match with opponent_id=<victim>, referee_waived=true, status='pending_confirmation', winner_id=<self>, result='submission', result_proposed_by=<victim>. Then call confirm_match_result(match_id, true): the guard is only 'auth.uid() = m.result_proposed_by' blocks the PROPOSER (leagues.sql:397), and since result_proposed_by was forged to the victim, the attacker 'confirms' their own claim and _settle_match transfers real rating (+wager, allowed up to 10% of ROR) from a user who never accepted any challenge. No video check exists on the confirm path. Attack 2: insert status='completed', winner_id=self, submission_type='Heel hook' etc. - these fabricated rows feed every quest counter (claim_quest counts matches where status='completed' and winner_id=uid, daily-quests.sql:78), claim_submission_rewards (+15 per type), king-slayer/globetrotter/streak progress, and tournament_standings_pro (counts completed matches by tournament_id, tournaments-pro.sql:674) - free rating and fake standings.
- **At 100k users:** At 100k users this is a scripted rating-theft/leaderboard-forgery primitive: one paid account can drain rating from any user in the wager band and fabricate unlimited quest/standings wins; leaderboard and season integrity (the product's core value) is destroyed as soon as one person discovers it.
- **Evidence:** `schema.sql:277-279: create policy "matches_insert_as_challenger" on public.matches for insert to authenticated with check (challenger_id = auth.uid()); -- no revoke/column grant on matches exists in any file. leagues.sql:391-400 (confirm_match_result): if m.status <> 'pending_confirmation' then raise ...; if auth.uid() = m.result_proposed_by then raise ...; return public._settle_match(m.id, m.winner_id, m.result, ...) -- winner_id/result/result_proposed_by are trusted from the row the attacker inserted.`

### 3. grant_comp_entitlement is callable by any client via PostgREST — permanent free-access self-grant (paywall bypass)
- **File:** `supabase/subscriptions.sql:99`  | **Area:** entitlements-paywall / security / paywall bypass
- **What/why:** grant_comp_entitlement is SECURITY DEFINER and writes a never-expiring source='comp' entitlement (comp rows are unconditionally active in has_active_entitlement). The comment says it is 'Not granted to authenticated', but in Postgres CREATE FUNCTION grants EXECUTE to PUBLIC by default, and Supabase exposes every executable public-schema function at /rest/v1/rpc/. There is no REVOKE anywhere in the repo for this function (grep for 'grant_comp_entitlement' + 'revoke' confirms). Other files show the correct hardening pattern (e.g. written-puzzles.sql:70 'revoke execute on function public.submit_puzzle_written ... Any user (even anon-key holders, since PUBLIC includes anon) can POST /rest/v1/rpc/grant_comp_entitlement {"p_user":"<their uuid>"} and get free access forever; they can also grant it to arbitrary other users.
- **At 100k users:** At 100k users someone will enumerate the RPC namespace (it is discoverable via the OpenAPI endpoint) and the exploit will circulate; every exploiter is a permanently unentitled-but-active account with zero revenue, and cleanup requires distinguishing legit comps (app review, elite, founders) from stolen ones.
- **Evidence:** `subscriptions.sql:99-107: `create or replace function public.grant_comp_entitlement(p_user uuid, p_note text default null) returns void language sql security definer set search_path = public as $$ insert into public.entitlements ... values (p_user, coalesce(p_note,'comp'), 'comp', 'active', null) on conflict (user_id) do update set source='comp', status='active', expires_at=null ...` — no `revoke execute ... from public` follows (only `grant execute` statements exist in the file, lines 92-93, and none mention this function).`
- **Fix:** Add `revoke all on function public.grant_comp_entitlement(uuid, text) from public, anon, authenticated;` to subscriptions.sql and run it against prod immediately. Also audit prod: `select user_id, product_id from entitlements where source='comp'` for rows you didn't create.

### 4. One purchased subscription can entitle unlimited accounts — validate-purchase never checks whether the transaction is already claimed by another user
- **File:** `supabase/functions/validate-purchase/index.ts:132`  | **Area:** entitlements-paywall / paywall bypass
- **What/why:** validate-purchase entitles the caller (`user_id = userId` from the JWT) based on any valid Apple transactionId or Google purchaseToken, with no check that the transaction isn't already bound to a different user_id. entitlements has PK user_id and only a NON-unique index on original_transaction_id (subscriptions.sql:39-40 `create index if not exists idx_entitlements_orig`). So user A buys one $4.99 sub, shares the transactionId/purchaseToken (trivially observable from their own device/receipt) with N friends who each create accounts and call validate-purchase — all N get active rows backed by the same store subscription. Compounding bug: apple-notifications/index.ts:59-64 uses `.maybeSingle()` on `.eq('original_transaction_id', ...)`; with 2+ rows sharing the id, maybeSingle errors, `row` is null, and the function returns without updating — so renewals/refunds/cancellations for that subscription are never processed for ANY of the claimants (they keep 'active' with a stale expires_at until it passes, and refunds are never revoked).
- **At 100k users:** At 100k users this becomes the shared 'family hack': one sub per friend group. Revenue leak scales linearly with virality, and the maybeSingle failure silently disables lifecycle sync for exactly the abused subscriptions, so even refunded originals keep everyone active.
- **Evidence:** `validate-purchase/index.ts:132: `const { error: upErr } = await admin.from('entitlements').upsert(row, { onConflict: 'user_id' });` — no prior query for an existing row with the same original_transaction_id and a different user_id. subscriptions.sql:39: `create index if not exists idx_entitlements_orig on public.entitlements (original_transaction_id);` (not unique).`
- **Fix:** In validate-purchase, before upserting, `select user_id from entitlements where original_transaction_id = <id> and user_id <> userId`; if found, reject (409) or transfer per policy. Back it with a partial unique index: `create unique index on entitlements (original_transaction_id) where original_transaction_id is not null and source <> 'comp'`. In apple-notifications, replace maybeSingle with a plain select and handle 0/1/many explicitly.

### 5. Parental-consent approval link is handed directly to the minor when RESEND_API_KEY is unset — teen self-approves own account
- **File:** `supabase/functions/request-parent-consent/index.ts:81`  | **Area:** auth-minors / minors/consent bypass
- **What/why:** The request-parent-consent function is callable by the signed-in minor themselves. When RESEND_API_KEY is not configured (the email flow is explicitly documented as optional, and per project notes the Resend flow is still parked/undeployed), the function returns the verify-parent-consent URL, token included, in the JSON response to the minor's own client. The minor opens the link and verify-parent-consent flips profiles.consent_status to 'verified' with no parent involved. Every server-side teen restriction (match trigger, open_for_challenge, public visibility) keys off consent_status='verified', so this is a full bypass of the app's entire parental-consent model. Even when Resend IS configured, parent_email is whatever the teen typed at signup (sign-up.tsx line 102) with zero verification that it belongs to an adult or a parent — a teen enters their own second email and one-click approves themselves.
- **At 100k users:** At 100k users (~thousands of 14-17 accounts), the restricted-teen state is fiction: any teen who watches one network request self-approves. App Store child-safety representations and the terms' consent model are false in production.
- **Evidence:** `request-parent-consent/index.ts:80-81: `// No email provider configured yet — return the link so it can be shared manually.\n  return json({ ok: true, sent: false, link, parent_email: pc.parent_email });` where `link = ${base}/verify-parent-consent?token=${pc.token}` (line 48). verify-parent-consent/index.ts:36-44 sets `status: "verified"` and `consent_status: "verified"` for whoever presents the token.`
- **Fix:** Never return the link/token to the authenticated caller — if no email provider is configured, return an error and block teen signups until it is. Verify the parent by a stronger signal than an emailed GET link (at minimum: parent creates/holds their own account, or reply-with-code flow), and reject parent_email equal to the account's own email.

### 8. _settle_match() (the raw Elo/wager settlement engine) is PUBLIC-executable with no caller/status check — any user can force-complete any match, award themselves the win, and swing ratings/wagers arbitrarily
- **File:** `supabase/match-waive-and-wager.sql:38`  | **Area:** rls-security / SECURITY DEFINER missing caller check / rating integrity
- **What/why:** _settle_match is SECURITY DEFINER and by design does no authorization ('Callers do their own auth first' per the header comment). It is created without any `revoke execute from public`, so it inherits the default PUBLIC EXECUTE grant and is reachable as PostgREST RPC POST /rest/v1/rpc/_settle_match. It takes an arbitrary p_match_id + p_winner_id, recomputes Elo, applies the wager transfer, and writes status='completed' with new ratings — for ANY match, regardless of whether the caller is a competitor/referee and regardless of the match's current status. Match ids are world-readable (matches_read_all using(true)). An attacker can therefore: (a) settle any match they are in with themselves as winner plus the wager swing, (b) re-call it on already-completed matches to repeatedly pump their rating, (c) force a rival's pending match to a loss. This bypasses all the guarded entry points (record_match_result/confirm_match_result) that normally gate who may score.
- **At 100k users:** At 100k users the leaderboard and wager system become meaningless — anyone can mint rating and win wagers on demand, and the ratings that gate wager bands / matchmaking are corruptible in bulk, destroying the core competitive product.
- **Evidence:** `create or replace function public._settle_match(p_match_id uuid, p_winner_id uuid, p_result result_type, p_method text, p_notes text)
 returns public.matches language plpgsql security definer ... as $$
 begin
   select * into m from public.matches where id = p_match_id for update;   -- no participant/status check
   ... c_new := c_new + m.wager; o_new := o_new - m.wager; ...
   update public.profiles set rating = c_new ... where id = m.challenger_id;
   update public.matches set status = 'completed', winner_id = p_winner_id ...;
 $$;   -- no `revoke execute ... from public`; header comment: 'C`
- **Fix:** revoke execute on function public._settle_match(uuid, uuid, result_type, text, text) from public, anon, authenticated; (it only needs to be callable by the other SECURITY DEFINER functions, which run as owner and are unaffected by the revoke). Optionally rename to a non-RPC-exposed schema.

### 10. 10k-16k filtered postgres_changes subscriptions on public.matches at 2k concurrent clients - two orders of magnitude past Supabase's guidance
- **File:** `src/app/(tabs)/index.tsx:66`  | **Area:** realtime-scale / realtime-architecture
- **What/why:** Every signed-in client holds 5 permanent filtered postgres_changes bindings on public.matches, rising to 8 after visiting the Matches tab: home screen channel 'home-matches' has 3 bindings (challenger/opponent/referee, src/app/(tabs)/index.tsx:66-71), 'pending-count' in the tab LAYOUT (always mounted while signed in, src/app/(tabs)/_layout.tsx:10 + src/hooks/use-pending.ts:41-45) has 2, and 'matches-tab' (src/app/(tabs)/matches.tsx:53-58) has 3 more; react-navigation tabs keep screens mounted after first visit, so none of these unmount. Plus 1 binding on public.notifications per client (src/hooks/use-unread.ts:33-36). With postgres_changes, Realtime's apply_rls evaluates EVERY committed change on a subscribed table against EVERY subscription's filter (and RLS) inside Postgres - cost is O(subscribers x events) on a single sequential WAL stream per publication. Supabase's own guidance is that filtered postgres_changes degrades beyond a few hundred subscribers per table.
- **At 100k users:** At 2k concurrent clients: 2,000 x (5-8) = 10,000-16,000 subscription rows on public.matches and 2,000 on public.notifications. Every match INSERT/UPDATE (each match lifecycle = 1 insert + 2-3 updates, plus the notify_match_* triggers insert 2 notification rows per transition, which hit the 2k notification subscriptions) triggers ~13,000 filter/RLS evaluations in realtime.apply_rls. At even 3k matches/day (~9k matches events + ~20k notification inserts, concentrated in evening peak), that is on the order of 150-200M subscription evaluations/day running inside the database. The realtime worker falls behind WAL: events arrive seconds-to-minutes late, then subscriptions time out and channels error/close, and DB CPU is burned on apply_rls instead of queries. This is 20-30x past the point where Supabase says filtered postgres_changes stops scaling.
- **Evidence:** `index.tsx:67-70: .channel('home-matches').on('postgres_changes', { ... table: 'matches', filter: `challenger_id=eq.${userId}` }, ...).on(... filter: `opponent_id=eq.${userId}` ...).on(... filter: `referee_id=eq.${userId}` ...); use-pending.ts:42-44 (same table, 2 more filters, mounted from _layout.tsx:10); matches.tsx:54-57 (3 more). Publication: supabase/schema.sql:285 'alter publication supabase_realtime add table public.matches;'`
- **Fix:** Two-step. (1) Immediate: consolidate to ONE matches channel per client - lift the subscription into a context/store (e.g. a useMyMatchesRealtime provider) that the home screen, matches tab, and pending badge all read from; that cuts bindings from 8 to 3 (or 1 if you filter client-side on a single or() ... not supported, so 3). ### 11. No UNIQUE constraint on entitlements.original_transaction_id - one Apple/Google subscription entitles unlimited accounts (paywall bypass)
- **File:** `supabase/subscriptions.sql:31`  | **Area:** triggers-rpcs / missing constraint / paywall
- **What/why:** entitlements is keyed PK user_id only; original_transaction_id has a plain (non-unique) index. validate-purchase upserts with onConflict:'user_id' and never checks whether the same original_transaction_id / purchaseToken is already attached to a DIFFERENT user, and never verifies StoreKit appAccountToken against the caller. Concrete bypass: user A buys the $4.99 sub; signs out; friend B signs into their own account on the same device (or A shares the iCloud/Play account); taps Restore Purchases; StoreKit/Play returns the same transaction; client posts it to validate-purchase; the function validates it with Apple/Google (it IS valid) and upserts an active entitlement row for B's user_id with the same original_transaction_id. - **At 100k users:** At 100k users this is the dominant revenue leak: whole training groups share one subscription; with ~10k DAU a 5:1 sharing ratio silently cuts subscription revenue by 80% and is undetectable from the entitlements table because every account looks legitimately active.
- **Evidence:** `subscriptions.sql:21-40: user_id uuid primary key ... original_transaction_id text; create index if not exists idx_entitlements_orig on public.entitlements (original_transaction_id); -- no unique. functions/validate-purchase/index.ts:132: await admin.from('entitlements').upsert(row, { onConflict: 'user_id' }); -- no cross-user original_transaction_id check anywhere in the function.`
- **Fix:** Add: create unique index entitlements_orig_txn_uniq on public.entitlements (original_transaction_id) where original_transaction_id is not null and source <> 'comp'; and in validate-purchase, before upserting, select any existing row with the same original_transaction_id and reject (or explicitly re-home with sign-out of the old user) when its user_id differs from the caller. Also pass and verify appAccountToken=userId on iOS purchases.

### 12. record_bout_result has no bout-status guard - double invocation creates two matches and applies Elo twice
- **File:** `supabase/tournaments-pro.sql:579`  | **Area:** triggers-rpcs / race condition / idempotency
- **What/why:** record_bout_result locks the bout row (for update) but never checks b.status, unlike record_subbout which raises 'Bout already finished' (line 626). Interleaving: the mat referee and the host both tap Record on the same live bout (or one client retries after a network timeout - the app has no idempotency key). Call 1: locks bout, inserts a matches row, _settle_match applies rating to both profiles, sets bout done, advances winner. Call 2 (blocked on the row lock until commit, or arriving seconds later): passes _may_record, passes the a_entrant/b_entrant checks, inserts a SECOND matches row for the same physical bout and settles it - both competitors' ratings move twice (and season points accrue twice via trg_accrue_season on the second completed transition... on both, actually). If the second call reports a different winner it also silently overwrites winner/match_id and pushes a different person into next_bout, corrupting the bracket after the first winner was already advanced into the parent bout's slot.

- **What/why:** post_league_message inserts one public.notifications row per league member in the RPC transaction, and the documented delivery model ('A Supabase Database Webhook on INSERT of that table calls the send-push edge function', push-notifications.sql header lines 5-9; same in send-push/index.ts:1-7) fires one HTTP call per inserted row via pg_net. Each send-push invocation then makes 2 extra DB round trips (profiles.notif_prefs select + expo_push_tokens select) and its own Expo POST for a single recipient. A 500-member league announcement therefore queues 500 pg_net requests, 500 edge-function cold/warm invocations, ~1000 DB queries, and 500 single-message Expo POSTs (Expo accepts 100 messages per POST). The same per-row pattern applies to notify_league_matchup, which inserts 2 rows per fixture for a whole league's weekly schedule generation in one transaction.
- **At 100k users:** At 100k users with 1k-member leagues, one announcement bursts 1k pg_net rows and 1k edge invocations; a few organizers posting at once saturates the pg_net worker and edge-function concurrency, delaying ALL pushes (including match challenges) by minutes and bloating net.http_request_queue.
- **Evidence:** `push-notifications.sql:165-172: insert into public.notifications (user_id, type, title, body, data) select m.user_id, 'league_message', ... from public.league_members m where m.league_id = p_lid and m.user_id <> auth.uid(); -- and send-push/index.ts:2-3: 'Database Webhook target for INSERTs on public.notifications ... fires this function on each INSERT', :55/:61 per-invocation profile + token selects, :80 one fetch per <=100 tokens of ONE user.`
- **Fix:** For bulk types (league_message, league_matchup) skip the per-row webhook and send from the RPC path via a single batched edge-function call (or a queue table drained by a cron) that fetches all members' prefs and tokens in two set-based queries and posts to Expo in 100-message chunks.

### 74. _settle_match locks the two profile rows in challenger-then-opponent order - reversed-role concurrent settlements can deadlock
- **File:** `supabase/leagues.sql:269`  | **Area:** triggers-rpcs / concurrency / deadlock
- **What/why:** Every settlement path locks profiles in match-role order: challenger first, then opponent. If two completed-at-the-same-moment matches exist between the same two users with roles reversed (A challenged B in match 1, B challenged A in match 2 - common for rematches, or a league fixture plus a casual match), and both settle concurrently: T1 locks profile A then waits for B; T2 locks profile B then waits for A. Postgres detects the deadlock after deadlock_timeout (1s) and aborts one transaction; that referee's record_match_result fails with '40P01 deadlock detected' and the client shows a raw error. No data corruption (the aborted txn rolls back fully), but the settle appears to the user as a random failure.
- **At 100k users:** At 1-2k concurrent clients with active rematch pairs and league nights, sporadic 'deadlock detected' failures surface as flaky result-recording that support cannot reproduce.
- **Evidence:** `leagues.sql:269-270 (and identically match-waive-and-wager.sql:54-55, tournaments-pro.sql:190-191, ror-symmetric-stake.sql:49-50): select rating into c_rating from public.profiles where id = m.challenger_id for update; select rating into o_rating from public.profiles where id = m.opponent_id for update;`
- **Fix:** Lock in deterministic global order: select the two profile rows in a single statement ordered by id (select id, rating from public.profiles where id in (m.challenger_id, m.opponent_id) order by id for update) and map ratings back to roles afterwards.

### 75. grant_elite quota is count-then-insert - concurrent grants let a founder exceed the 10 comp-membership cap
- **File:** `supabase/elite-memberships.sql:46`  | **Area:** triggers-rpcs / race condition / comp entitlement cap
- **What/why:** grant_elite counts the founder's existing grants and raises if used >= 10, then inserts and calls grant_comp_entitlement.
